# Configuration

Where every TankLink setting lives, what it defaults to, and how to change it. Build and flash steps are in [`firmware-build-setup.md`](firmware-build-setup.md). Pin wiring is in [`PINMAPS.md`](PINMAPS.md).

## How settings are layered

Each firmware node has two kinds of setting.

**Build options** are compiled into the firmware. They hold pins, timings, and which hardware is enabled. They come from three layers, and the later one wins:

| Layer | File | In git? | Purpose |
| --- | --- | --- | --- |
| 1. Kconfig default | `<node>/main/Kconfig.projbuild` | yes | Fallback and help text for each option |
| 2. Project defaults | `<node>/sdkconfig.defaults` | yes | **The real values for this project.** Change pins here |
| 3. Local config | `<node>/sdkconfig` | **no** (gitignored) | Generated by the build from layers 1 and 2, then edited by `menuconfig` |

**Runtime settings** are changed from the app and saved in the board's flash (NVS). Examples are auto-off time, buzzer, LED brightness, starter type, and float mode. They survive firmware updates. They are cleared by a factory reset or `idf.py erase-flash`.

### Changing a build option

1. Edit `<node>/sdkconfig.defaults`, so the change is committed and every build uses it.
2. Make your local `sdkconfig` pick it up. The build only copies defaults into `sdkconfig` for options it doesn't have yet. **An option already in your local `sdkconfig` keeps its old value.** Do one of these:
   - edit the same line in `<node>/sdkconfig` by hand, or
   - delete `<node>/sdkconfig` and build again, which regenerates it from the defaults, or
   - run `idf.py menuconfig` → **Pump Board** / **TankLink Tank Node**, then copy the value back into `sdkconfig.defaults`.
3. Check the value took effect: `grep PUMP_RTC sdkconfig` (or whichever option you changed).

> `idf.py set-target esp32c3` also deletes `sdkconfig` and regenerates it from the defaults. Anything you set only in `menuconfig` is lost.

A new option added to `Kconfig.projbuild` needs a matching line in `sdkconfig.defaults` too, so its intended value is written down in one place.

## Runtime settings (set from the app)

Stored on the pump in NVS namespace `pump`, key `cfg`. Defaults apply after a first flash or factory reset.

| Setting | Default | Range / values | App location |
| --- | --- | --- | --- |
| Auto-off (per tank) | 30 min | 1 – 240 min (can't be turned off) | Pump settings. Stored with the tank slot in `tl_tanks` |
| Install updates automatically | off | on / off, needs Wi-Fi; only when the pump is idle and no fill is planned | Pump settings. `auto_update` in `pump` `cfg` |
| Auto-fill (per tank) | off | on / off, only for a tank with both floats | Pump settings → Fill when low. `auto_fill` in `tl_tanks` |
| Water and power | flow not set, 750 W, price not set, ₹ | flow (L/min), power (W), price per kWh, currency | Water and power → Pump details. `usage` in `pump`, its own key, so it never resets the other settings |
| Buzzer | on for button, pump start/stop, auto-off | per-event switches | Pump settings |
| Buzzer tone | click | click, soft, sharp, double | Pump settings |
| LED brightness | 70 % | 1 – 100 % | Pump settings |
| **Starter type** | **none** | none, two-button | **Starter** |
| Relay pulse | 1000 ms | 50 – 2000 ms | Starter |
| Second float (per sensor) | off | off, almost-empty, two tanks | Tank sensors → a sensor. Stored with the sensor in `tl_tanks` |

> **The starter type defaults to "none".** In that mode the pump tracks on/off and the LED, but never pulses the relays. A new or factory-reset pump needs **Starter → two-button** set in the app before it will actually run a motor.

Other data the pump saves (all cleared by factory reset or `erase-flash`):

| NVS namespace | Holds |
| --- | --- |
| `pump` | Runtime settings above, and the pump's name (`name`, up to 24 bytes of UTF-8; cleared by factory reset) |
| `tl_pair` | Phone pairing: one 16-byte token per phone (up to 8) and which are in use |
| `tl_tank` | Per paired sensor N: its LoRa link key (`key<N>`, the BLE OTA token is derived from it), the last seq it accepted (`seq<N>`, so replays stay refused after a restart) and its last packet (`last<N>`, for restoring last-seen after a restart). |
| `tl_tanks` | Paired sensors (up to 4: MAC, float mode), tank slots (up to 8: sensor, which float, name, auto-off), and the selected tank (`slots`). Auto-fill per slot as a bit mask (`auto_fill`). |
| `tl_sched` | Fill schedules (up to 4) |
| `tl_wifi` | Optional Wi-Fi: network name (`ssid`) and password (`pass`). Cleared by factory reset and Forget Wi-Fi. Without them Wi-Fi never starts |
| `tl_alert` | The alert key (`key`, 16 bytes; made when a signed-in phone first reads it, replaced when phones are removed) and the last alert number (`seq`) |
| `tl_upd` | Version the pump started installing by itself (`overnight`), until the app has shown the notice |
| `tl_clock` | The phone's UTC offset in minutes (`utc_off`, i16), sent with every time sync, so SNTP can set local time |
| `tl_hist` | The last 200 fills: start, length, tank, start and stop cause |
| `tl_bat` | Each sensor's daily battery low and high for 14 days (`b<N>`) |
| `tl_run` | "Pump is running" record while a fill runs (refreshed each minute), and the interrupted-fill notice until it is dismissed |

The tank saves its pairing, its LoRa link key (`link_key`) and its packet counter (`seq32`) in NVS namespace `tank`.

The pump's **time** is not in NVS. It lives in the DS3231, is set by the phone, and isn't cleared by factory reset.

## App configuration

| Item | Where |
| --- | --- |
| Version + Android versionCode | `tanklink_app/pubspec.yaml` (`version: X.Y.Z+N`) |
| Android package ID | `com.tanklink.tanklink` (`android/app/build.gradle.kts`) |
| Min Android | API 24 (Android 7.0) |
| Release signing | `android/key.properties` + upload keystore. A release build fails without them; see [`app-release.md`](app-release.md) |
| Backup | Off (`allowBackup=false`, `data_extraction_rules.xml`): pump tokens never leave the phone |
| Saved pumps | Secure storage (`flutter_secure_storage`, key `saved_pumps`): name, device and sign-in token per pump |
| Water and power | Nothing on the phone: flow, power, price and currency are pump settings (`usage` in NVS namespace `pump`, Cmd `0xA9`), and the fills come from the pump's history |
| Update source | GitHub Releases on this repo (`app-v*`, `pump-v*`, `tank-v*`). Highest semver wins, among firmware whose manifest matches the app's protocol major and the board's revision |
| BLE UUIDs / opcodes | `lib/ble/tanklink_uuids.dart` |

## Memory (pump)

The ESP32-C3 has about 320 KB of RAM. With Bluetooth and Wi-Fi up and no phone busy, about **80 KB** of heap is free. The tightest moment is the pump downloading its own update over HTTPS (TLS buffers, the certificate check and the Wi-Fi packets at once): measured with a dry run of the real 725 KB GitHub download, the lowest free heap was **about 39 KB**, with the largest free block about 32 KB. The pump logs this (`UPDATE: heap ...`, and `DIAG: heap ...` every 30 s) so it can be checked after any change.

What keeps it that way (`pump_node/sdkconfig.defaults`, each with a comment): Wi-Fi code in flash, not IRAM; station mode only; fewer Wi-Fi and lwIP buffers and sockets; no receive aggregation; TLS buffers allocated when needed; and the certificate bundle with cross-signed roots (without it every HTTPS connection fails). In code: the Wi-Fi API receive buffer starts at 0.5 KB per client and grows only for an OTA chunk (2 KB); the update runs on a short-lived 6 KB task.

Free flash in the OTA slot: about 18% (the image is about 1.5 MB of 1.75 MB). A change that adds more than ~200 KB needs a smaller feature set or a bigger partition table (which needs an `erase-flash` over USB).
